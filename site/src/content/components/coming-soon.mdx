## Overview

Coming Soon is a public editorial launch or maintenance page with a required
heading, optional decorative background, brand, supporting copy, real social
destinations, a target-owned native form, and contextual footer. Password
authentication and Countdown are not modes of this component.

## Presentation

The root establishes a named inline-size container. Wide component hosts use an
editorial/form split; narrow hosts preserve the same editorial-first source
order in one column. The required heading is a render precondition. Background
media is atmospheric and decorative because all essential content remains in
the page text.

The optional form region composes the complete Input anatomy and a
submit-capable Button. Coming Soon controls only its placement. Input retains
label, native field, message, validation, focus, disabled/read-only, value and
controlled/uncontrolled ownership. Button retains action states and pending
semantics. Social destinations compose canonical Link and keep native
navigation.

Shopify's public Coming Soon section maps this page. Shopify's separate password
template owns `storefront_password` and is not neutral Coming Soon anatomy.
Countdown time, timezone, cadence, correction, expiry and post-expiry content
remain unresolved product and architecture decisions.

## Usage Guidelines

<DoDont>
  <Do>Keep the page public, focused, truthful, and limited to essential editorial content plus one clear next step.</Do>
  <Dont>Do not use Coming Soon as authentication, imply a successful signup before the target responds, or infer a Countdown.</Dont>
</DoDont>

- Supply a non-empty visible heading and keep essential information textual.
- Use real Link destinations and meaningful labels; do not prevent activation
  or point to missing fragments.
- Ask only for data the target actually needs and explain what visitors will
  receive.
- Let the target own endpoint, consent, pending state, success, error, retry,
  analytics, persistence, and publication scheduling.
- Treat fixture copy, destinations and email feedback as evidence, not component
  defaults or service guarantees.

## Accessibility

- Use one `main` landmark in a standalone target page. Inside another page such
  as this documentation, render a labelled contextual `section` instead.
- Keep the required visible heading present and omit invalid required
  composition.
- Use `alt=""` for atmospheric background images and never encode essential
  content only in media.
- Preserve editorial-first source and reading order when the component stacks.
- Compose social destinations from native anchors with truthful `href` values.
- Compose form controls from Input with a visible label, native type,
  `required` when applicable, and an associated message. Preserve native email
  constraint validation.
- Use a native submit-capable Button. Announce or navigate to truthful target
  feedback; a local preview must state that it made no request.
- Emit a form label relationship only when its visible heading exists. Omit an
  empty form region.
- Preserve Canvas/CanvasText legibility in forced colors. Coming Soon adds no
  motion of its own.
