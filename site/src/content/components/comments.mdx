## Overview

Comments presents a required heading, optional target-formatted count, target-owned comment thread, and optional target-owned composer. It supplies static editorial structure without defining discussion-service behavior.

The component has one fluid threaded presentation. Comment records use `.comment`; author, date, text, actions, and nested replies use their canonical elements. The optional `.comment-form` composes Textarea and Button controls but remains a target-owned slot.

## Usage Guidelines

<DoDont>
  <Do>Supply comment data, nesting, controls, and form handling from the target integration.</Do>
  <Dont>Do not infer sorting, reply logic, authentication, moderation, optimistic updates, or count synchronization from the static classes.</Dont>
</DoDont>

Which comment behaviors belong to the neutral component and which belong to targets remains unresolved. Until that boundary is accepted, thread actions and the composer are presentation slots rather than a neutral discussion API.

## Accessibility

- Use semantic lists or another structure that communicates comment and reply relationships without relying on indentation alone.
- Expose author and date text clearly; use `time` with a machine-readable `datetime` value when available.
- Use native buttons for comment actions with descriptive names and visible focus.
- Keep Textarea labels, validation relationships, disabled state, and Button submission semantics intact.
- Provide target-specific accessible status handling for authentication, moderation, submission feedback, and live updates.
