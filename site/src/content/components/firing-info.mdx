## Overview

Firing Schedule presents one technically reviewed firing program through two required, synchronized forms: a temperature-over-real-time ramp chart and one canonical Data Table row per planned segment. It may compare a controlled observed series with the plan, but it never programs, starts, controls, polls, validates, or certifies a kiln.

`firing-info` remains the internal pre-v1 migration slug. The public component name and canonical root selector are Firing Schedule and `.firing-schedule`; legacy Kiln / Firing Info naming and `.firing-info` exist only until the public contract freezes.

## Presentation

The normalized source requires one finite `startingTemperatureCelsius` and one ordered non-empty `segments` collection. Every segment has a stable `segmentId`, a positive Celsius-per-hour rate or `full`, a target Celsius temperature, and a non-negative hold duration in seconds. Neutral source derives every planned ramp duration, accumulated time, chart point, and table duration from this single program.

A `full` segment must include a positive, target-reviewed `estimatedRampSeconds`. The table labels that duration as estimated. Without it, the complete schedule is invalid because the segment cannot be placed truthfully on the real-time horizontal axis.

Optional `actualSamples` are strictly increasing elapsed-second/Celsius observations controlled by the target. They draw one observed curve and never become thousands of table rows. Optional `actualSummaries` correlate observed duration, reached temperature, and deviation to planned rows through `segmentId`.

`view` accepts `planned`, `actual`, or `both`. When it is unset, valid observed data selects `both`; otherwise it selects `planned`. `actual` is unavailable without observations and safely resolves to `planned`. `displayUnit` defaults to `celsius`; `fahrenheit` converts the entire table, axes, summaries, and legend from the same normalized source rather than receiving duplicate datasets.

`actualStatus` is `collecting` or `complete`. A collecting series may be partial and is labelled as such. Target updates replace the controlled sample array at a bounded cadence; the component never connects to equipment and never announces each sample.

## Guidelines

<DoDont>
  <Do>Supply one technically reviewed normalized program, stable segment identifiers, real durations, provenance, and truthful collecting/complete observed data.</Do>
  <Dont>Do not use the component to enter controller commands, start a firing, infer material safety, or compare independently drawn planned data with the table.</Dont>
</DoDont>

- Preserve real accumulated time on the horizontal axis; ramp and hold widths must correspond to duration.
- Keep the canonical Data Table as the detailed representation and one row per planned segment.
- Use observed summary columns only when they are target-correlated to the matching stable `segmentId`.
- Keep safety procedures, equipment instructions, validation, alarms, live control, and technical approval in separately governed systems and content.
- Treat fixture temperatures, rates, holds, deviations, labels, and sample cadence as documentation evidence, not production defaults.

## Accessibility

- Render the chart as one informative `svg[role="img"]` with a non-empty localized `<title>`, concise `<desc>`, and visible `figcaption` summarizing visible series, time, range, lifecycle, and relevant deviation.
- Keep raw chart points out of sequential keyboard focus. The named chart scroll owner and canonical table scroll owner retain visible focus when horizontal scrolling is required.
- Preserve native table, caption, row/column headers, and `scope`; do not replace passive tabular data with a grid widget.
- Distinguish Planned and Actual with visible legend text plus dashed versus solid line treatment, not color alone.
- Do not put otherwise unavailable data only in hover tooltips and do not announce sample-by-sample updates.
- The Data Table is the primary long-form alternative for segment detail; the chart summary communicates the overall comparison without duplicating every raw sample.

## Specification

**Dependency:** canonical Data Table.

**Anatomy:** conditional `.firing-schedule` section/div; optional header/title; required visible summary; required informative chart, named scroll owner, axes, legend and caption; required `.firing-schedule__table` canonical Data Table with one row per planned segment. `.firing-info` is a temporary pre-v1 root alias only.

**Targets**

- **Neutral Web:** canonical CSS, native table/SVG markup, and framework-independent `components/js/firing-schedule.js` model; target owns localized labels and controlled source updates.
- **Shopify:** planned until a normalized schedule/observation source, technical validation, provenance, safety/editor policy, and first consumer are approved.
- **Webflow:** target code maps verified structured records to the neutral model; CMS strings alone are insufficient for the derived chart.
- **React / Angular:** thin view layer consumes the neutral model and canonical Data Table without a second planned-series store.
- **Figma:** future component covers planned/actual/both, Celsius/Fahrenheit, collecting/complete, narrow/wide scroll containment, long/localized data, themes, forced colors, and print; current generic references are not approval.
- **SwiftUI / Compose / future:** platform chart and native table/list share one normalized program and controlled observed stream; equipment connectivity remains outside the component.
