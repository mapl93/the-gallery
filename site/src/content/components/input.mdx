## Overview

Native single-line text input with form semantics, a visible label, optional message, validation variants, and independent passive icon slots.

## Presentation

Input has one default size and four validation variants. The absence of a modifier class selects the default variant.
Leading and trailing icons are optional, independent, and passive; they may be used together without changing the native field semantics.
Hover preserves the active Error, Success, or Warning color family instead of returning the border to Default.
Semantic borders and status icons use a private contrast-strengthening mix of their public validation token with primary text; the public token remains the customizable source value.

| Property | Value | Web mapping |
| --- | --- | --- |
| `variant` | `default` | `.input` |
| `variant` | `error` | `.input--error` |
| `variant` | `success` | `.input--success` |
| `variant` | `warning` | `.input--warning` |
| `size` | `default` | `.input` |

### Native form behavior

`name`, `required`, `readOnly`, `autocomplete`, `minLength`, and `maxLength` map directly to the native input. In static HTML, the `value` attribute establishes the initial value and the browser owns subsequent editing and reset behavior. Framework adapters may instead bind the live `value` property and native `input`/`change` events; they must not create a second hidden value owner.

The visible label or associated instructions must say when a value is required. `required` supplies constraint-validation semantics but does not replace that visible instruction.

## Usage Guidelines

<DoDont>
  <Do>Use Error for invalid values and Warning for values that need attention but can remain valid.</Do>
  <Dont>Do not communicate validation through border or icon color alone.</Dont>
</DoDont>

<DoDont>
  <Do>Keep labels visible and concise, and use placeholder text only as supporting guidance.</Do>
  <Dont>Do not use placeholder text as the field's only accessible name.</Dont>
</DoDont>

## Accessibility

<Callout type="info">
  Validation classes are visual. Native attributes provide the corresponding form semantics.
</Callout>

- Associate every input with a `<label>` using matching `for`/`id` attributes.
- Connect supporting and validation messages with `aria-describedby`.
- Add `aria-invalid="true"` when the error variant represents an invalid value.
- Do not add `aria-invalid` to Success or Warning; keep their associated message descriptive.
- Use native `disabled` for unavailable fields.
- Use `readOnly` when a value must remain focusable, selectable, and submittable but cannot be edited.
- Keep `name`, `required`, `autocomplete`, `minlength`, and `maxlength` on the native input.
- Communicate required status in visible label or instruction text instead of relying on the native attribute alone.
- Use `role="alert"` only when an error message is inserted dynamically; a message already present at page load only needs `aria-describedby`.
- Do not rely on icon or color alone to communicate validation status.
- Keep `leadingIcon` and `trailingIcon` passive and hidden from assistive technology when decorative.
- Use a specialized component such as Password Input when an icon performs an action.
