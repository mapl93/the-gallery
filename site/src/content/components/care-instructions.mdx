## Overview

Care Instructions presents passive, target-owned care guidance as a related text-first collection. It supplies durable document/list semantics and intrinsic responsive composition, not a checklist, alert, acknowledgement flow, product-care schema, claim validation, or target data service.

## Presentation

The required `items` slot supplies one or more complete target-owned records. Every item requires a stable identity and non-empty visible instruction label. Explanatory detail and redundant supporting icon are optional. `title` is optional.

With a title, the root is a named native section; without one, it is a generic container with no dangling label relationship. The collection is one native `ul` with direct `li` items. The compatibility selector `.care-instructions__grid` may coexist on that same list; it is not a second wrapper.

`variant` accepts `default`, `do`, or `dont`; `do` maps to `.care-instructions--do` and `dont` maps to `.care-instructions--dont`. Do and Don't change supporting icon color for one homogeneous set but create no status, validation, urgency, or accessible state. The visible heading and each instruction must communicate recommendation or prohibition without color or icon.

One instance always represents one homogeneous neutral, recommended, or avoid set. Compose separate Care Instructions instances for recommended and avoid guidance instead of adding per-item tone. Public semantic values remain `default`, `do`, and `dont`; targets may present friendlier localized visible vocabulary such as Recommended/Avoid.

The demonstrated wording, icons, heading level, item order, count, grid threshold, alignment, and treatment are fixture/presentation details, not defaults or a public product-care record schema.

### Behavior boundary

Care Instructions owns no controlled/uncontrolled value, selected/checked/completed/acknowledged state, event, focus, keyboard model, dismissal, disclosure, request, timer, persistence, live announcement, analytics, warranty, safety review, or claim validation.

If a product needs confirmation or choices, compose behavior-specific canonical components such as Checkbox, Radio, Button, Alert, Form, or a separately accepted workflow. Do not add their roles or states to passive R4 by implication.

### Responsive behavior

Canonical R4 CSS derives column count from the actual component width. Narrow hosts use one column; wider hosts add columns when each record retains its readable minimum. Complete labels and descriptions wrap without clamping. Studio owns no separate R4 breakpoint or margin correction.

## Guidelines

<DoDont>
  <Do>Write each instruction so its meaning and any recommendation or prohibition remain complete without the icon or color treatment.</Do>
  <Dont>Do not present generic fixture copy as verified care guidance for every product, material, finish, attachment, or jurisdiction.</Dont>
</DoDont>

- Use `default` for neutral information, `do` for one homogeneous recommended set, and `dont` for one homogeneous discouraged set.
- Keep labels concise and make optional details practical, qualified, product-specific, and current.
- Hide redundant icons from assistive technology; put unique meaning in visible text.
- Omit incomplete records and omit the root when no complete items remain.
- Keep safety, legal, editorial, localization, product applicability, revision, recall, and regulatory ownership in the target layer.
- Use another semantic composition for choices, acknowledgements, alerts, validation, status, warnings requiring interaction, or task completion.
- Keep legal or safety warnings in separately reviewed rich content or canonical Alert; never infer them from the care tone.

## Accessibility

- Use a contextual visible heading when the guidance is a thematic page section. Untitled compositions remain generic containers.
- Preserve one native `ul > li` collection. `role="list"` retains list exposure where visual markers are removed.
- Keep every required instruction label visible and understandable without icon, color, grid position, or item order.
- Mark redundant supporting icons `aria-hidden="true"`; do not add duplicate icon labels.
- Ensure Do/Don't meaning is present in visible authored wording, not inferred from green/red.
- Allow long, localized, RTL, zoomed, and user-spaced text to wrap without clipping or truncation.
- Do not add checkbox, option, alert, error, status, button, link, `tabindex`, selected/checked/acknowledged/completed state, roving focus, keyboard behavior, or live regions to passive neutral R4.

## Specification

Public visual tokens expose supporting icon size, intrinsic item minimum width, surface padding, header spacing, item rhythm and separate surface/header borders. Padding factors use the shared grid gap; text/content gaps use the shared element gap. Studio and Exhibit derive controls from the same public inventory.


**Dependencies:** None for the passive neutral implementation. A future confirmation or choice workflow composes separately accepted canonical behavior components rather than expanding R4 by implication.

**Anatomy:** conditional `.care-instructions` section/div; optional header and title; required native `.care-instructions__list.care-instructions__grid`; repeated direct native `.care-item` items; optional redundant icon; required visible label; optional complete description.

### Targets

- **Neutral Web:** conditional native section/div, `ul/li`, complete visible text, optional decorative icons, intrinsic canonical CSS, homogeneous supporting tone, and zero R4 JavaScript.
- **Shopify:** planned until product data source, content authority, safety/legal review, section/block schema, limits/order, localization, symbol policy, and first consumer are approved.
- **Webflow / React / Angular:** preserve native unordered children and target-owned content/claim lifecycle; keep acknowledgement or choices separate.
- **Figma / native targets:** represent optional title, repeated items, optional icon/detail, three treatments, and adaptive columns; registered generic Figma nodes are not R4 visual approval.
