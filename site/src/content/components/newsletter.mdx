## Overview

Newsletter Signup combines a native subscription form with Input and Button while leaving submission response behavior to the consuming target.

The form composes the complete Input anatomy: root, visible label, control, and native field. `.newsletter__input` is only a sizing hook on that native field; canonical CSS places the Input root and submit-capable Button. Optional field validation messages remain owned by Input.

## Usage Guidelines

<DoDont>
  <Do>State what subscribers will receive and collect only the information the subscription actually needs.</Do>
  <Dont>Do not use placeholder text as the email field's only label or imply a submission outcome before the target provides one.</Dont>
</DoDont>

Pending, success, error, retry, duplicate-submission and confirmed-result placement are target-owned under ADR 0251. The consuming target must implement and announce only its real outcome without treating this preview as a neutral default.

The shared Exhibit/Studio fixture intercepts a valid submission only to state `Preview only: no subscription was sent.` That truthful target-local message is not a neutral success state or service implementation.

## Accessibility

- Use a native `form`, a native `input` with `type="email"`, and a submit-capable Button.
- Associate the visible label with the field and connect supporting or validation text with `aria-describedby`.
- Preserve Input's Default, Error, Success, Warning, hover, focus-visible, and disabled obligations.
- Use `aria-invalid="true"` only for Error; Success and Warning keep descriptive messages without `aria-invalid`.
- Keep form-level submission results separate from the Email field's guidance or validation message.
- Announce or navigate to a clear submission result once the consuming target defines where that result lives.
