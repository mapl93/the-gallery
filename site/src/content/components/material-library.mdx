## Overview

Material Library presents a passive, target-owned collection of complete material references. It supplies durable document and collection structure, not a ceramics schema, selector, filter, resource manager, product catalogue, safety authority, or data service.

The accepted `R1-A` identity is passive: navigation, selection, comparison, and filtering are separate future product contracts rather than modes of Material Library. R0 keeps record provenance, localization, rights, applicability, measurements, and claim review in the target.

## Presentation

The required `materials` slot supplies one or more complete material records in target-owned source order. `title` and `subtitle` are optional. With a title, the root is a named native section; without one, it is a generic container with no dangling labelling relationship.

Each item is one native list item containing a passive, independently named material article. Its visible material name is required. Media, classification, description, and a native list of canonical passive Tags are optional and omitted independently.

The demonstrated names, classifications, descriptions, images, property labels, heading levels, and count are fixture content, not defaults or a public record schema.

### Behavior boundary

Material Library owns no controlled/uncontrolled value, event, hover state, selection, navigation, filter, sort, search, pagination, request, focus management, live result, or persistence. Targets compose truthful canonical controls only after those product behaviors are accepted.

### Responsive behavior

The collection responds to its actual host width through an intrinsic grid. Cards become one column when their container is narrow, not when the global viewport crosses a component breakpoint. Text remains complete and wraps in localized, RTL, unbroken, zoomed, and user-spaced conditions.

## Guidelines

<DoDont>
  <Do>Use concise material names, pair technical classification with plain-language context, and keep essential facts textual.</Do>
  <Dont>Do not treat the fixture as a CMS schema, use sample color as the only identifier, or imply whole-card interaction with passive hover styling.</Dont>
</DoDont>

- Keep target-authored records in a meaningful, documented source order.
- Compose canonical passive Tag for short property labels. Use explicit term/value semantics when facts need names and values.
- Use media only when it contributes useful context. Describe the actual image rather than claiming editorial imagery is a raw material sample.
- Omit incomplete records and omit the complete Material Library when no valid materials remain.
- Keep loading, empty, error, filters, search, safety claims, localization, product relationships, and analytics in the target layer.

## Accessibility

- Use a contextual visible heading when the library is a thematic page section. Untitled compositions remain generic containers.
- Preserve native `ul > li > article` structure and name every article from its visible material heading.
- Keep material names, classifications, properties, and all essential technical information available as text; do not rely on color, texture, or media alone.
- Give informative images a context-specific `alt`. Use `alt=""` when media is decorative or fully redundant with adjacent text.
- Do not add `grid`, `listbox`, option, roving-focus, or whole-card keyboard behavior to the passive collection.
- Canonical passive Tags have no remove action; a future interactive label requires the complete Tag or another canonical control contract.

## Specification

Public visual tokens expose card minimum width, media height, card padding, independent subtitle/classification/description/property spacing, tracking and border thickness. Shared layout, type and radius values remain editable. Studio and Exhibit use the same public inventory.


**Dependency:** [Tag](/components/tag).

**Anatomy:** conditional `.material-library` section/div; optional header, title, and subtitle; required native `.material-library__grid`; repeated native `.material-library__item`; one named native `.material-card` article per item; optional media; required body/name; optional type, description, and native property list containing canonical passive Tags.

### Targets

- **Neutral Web:** native conditional section/div, list/items/articles, semantic images, canonical Tags, intrinsic CSS, and zero R1 JavaScript.
- **Shopify:** planned until material source, editor schema, ordering/limits, product relationships, localization, and a first template consumer are approved.
- **Webflow / React / Angular:** preserve semantic children and keep CMS/query/action state outside R1.
- **Figma / native targets:** model optional context and repeatable complete cards without treating generic registered Figma nodes as visual approval.
