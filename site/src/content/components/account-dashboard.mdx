## Overview

Account Dashboard is a passive, labelled account-navigation overview. It composes a native destination list from canonical Card and Link, accepts optional target-owned account actions, and leaves customer data, authorization, routes, sign-out, privacy, and lifecycle state to the target.

## Presentation

The non-empty `greeting` is the visible contextual heading and programmatic name of the native section. The optional `headerActions` slot is omitted without an empty wrapper and should contain complete semantic target controls. `cards` is one required, non-empty composition slot rather than a flat property for each repeated item.

Each destination is a native `li.card.account-card` with canonical Card body/footer and one explicit `a.link.account-card__link`. Titles, optional descriptions, decorative icons, destinations, count, order, permission filtering, and target records remain fixture or target data. Whole-card activation is not inferred.

The root is a named inline-size container. Its private layout moves from one to two to three tracks according to available component width; columns are not a public semantic property.

## Usage Guidelines

<DoDont>
  <Do>Render only complete, available destinations derived from authenticated target state.</Do>
  <Dont>Do not expose sensitive summaries, unavailable routes, or working-looking actions without target behavior.</Dont>
</DoDont>

- Use Link for account destinations and Button for commands such as sign-out; do not blur navigation and actions.
- Keep each link label understandable in its card context and preserve native destination URLs.
- Omit optional descriptions, icons, and header actions when unavailable. Omit the complete renderer when greeting or the required destination list is invalid.
- Let the target own loading, authentication expiry, errors, no-destination policy, sign-out effects, redirection, feedback, focus, and analytics.

## Accessibility

- Label the native section from the visible heading with `aria-labelledby`; choose heading rank from the surrounding page outline.
- Preserve native `ul`/`li` semantics. CSS grid does not require `role="grid"`, roving focus, or arrow-key behavior.
- Give every destination a real native Link with a descriptive visible label; preserve Tab, Enter, modified activation, history, and canonical focus treatment.
- Keep text-complete icons decorative and hidden from assistive technology.
- Do not add a live region, automatic focus move, landmark, or custom keyboard model to the passive shell.
- Allow long, localized, bidirectional, and unbroken content to wrap in narrow and zoomed containers.

## Target Notes

- Neutral Web maps to the labelled section and native list shown above with zero U3 runtime.
- Target-controlled account views project authorized data and real routes through canonical U3. Platform-owned non-replaceable screens use a documented native handoff and do not claim visual or functional parity.
- Shopify v1 themes use the controlled `shopify-account` sheet and hosted account pages, so they intentionally omit a theme-owned U3 clone. Full-page extensions and headless Customer Account API views are distinct target-controlled projections; classic Liquid remains separately versioned compatibility.
- React and future framework targets should keep data, routing, authorization, actions, feedback, and lifecycle state external while preserving native dependency semantics.
- The registered Figma nodes resolve to generic Button documentation, not U3 artwork or visual approval.
