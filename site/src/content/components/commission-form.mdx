## Overview

Commission Form supplies a bounded introduction and layout profile for target-owned canonical controls, optional reference upload, and explicit actions. It does not prescribe commission fields, consent, submission, storage, notifications, or later workflow.

## Presentation

The interactive Exhibit/Studio fixture uses the same structure and sample copy as this fallback. It composes canonical Input for required name and email, canonical Textarea for a required request, canonical File Upload for one optional local reference, and canonical Button for submit/reset. The sample inventory demonstrates native form behavior; it is not a Commission Form schema or component default.

`fields` is required and an empty required slot omits the complete component. `title`, `intro`, `referenceUpload`, and `actions` omit independently. A standalone Web target uses a real form; a target already inside a form uses a non-form host and must not nest forms.

The local renderer uses native required/type/name/autocomplete behavior, FormData, one native FileList, native reset, and a concise polite message that explicitly says nothing was submitted or uploaded. Real validation, pending, success, failure, consent, persistence, and notifications remain target workflow.

## Guidelines

<DoDont>
  <Do>Compose canonical named controls and explicit native action types in logical source order.</Do>
  <Dont>Do not add a universal field schema, duplicate dependency validation, fake remote success, or assume that accepted file types provide server validation.</Dont>
</DoDont>

- Ask only for information the approved commission process needs.
- Keep visible labels, required status, format and file-policy guidance with the canonical control that owns them.
- Preserve one value owner per text control and one native FileList owner; controlled and uncontrolled strategies must not compete.
- Treat `accept` as a picker hint. The receiving target validates type, size, contents, security, storage, and deletion.
- Preserve entered valid values when reporting errors; longer forms may need a target-owned linked error summary.
- Use native reset when the target intends to restore default values. A generic destructive “Clear” action is not an R8 behavior.

## Accessibility

- Use a native standalone `form` or a non-form embedded host; never nest form elements.
- Associate every field with a visible label and place instructions before they are needed.
- Give submitted controls stable names, use explicit button types, and preserve native constraint validation, submitter, FormData, and reset unless the target owns a complete accessible replacement.
- Keep source, visual, reading, and keyboard order aligned when actions stack.
- Preserve canonical Input, Textarea, File Upload, and Button focus, disabled, validation, busy, forced-color, and reduced-motion behavior.
- Provide concise target-owned submission feedback and deliberate error-summary announcement/focus behavior without erasing valid entries.

## Specification

**Dependencies:** [Input](/components/input), [Textarea](/components/textarea), [File Upload](/components/file-upload), and [Button](/components/button).

**Anatomy:** `.commission-form`, optional header/title/text, required `.commission-form__fields`, optional `.commission-form__upload-zone`, and optional `.commission-form__actions`. Dependency anatomy and target-owned result/error summaries remain outside R8 ownership.
