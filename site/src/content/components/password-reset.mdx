## Overview

Password Reset is a passive, labelled recovery-request shell. It composes a complete canonical Form, Input, and Button, with optional confirmed feedback supplied through canonical Alert. The target owns the request and security lifecycle.

## Presentation

The required `title` labels the native section. Required guidance explains the request without revealing account existence. The optional `icon` is passive and decorative. `form` is a complete canonical Form slot; fields, actions, validation, and request state are not duplicated inside U2.

`successMessage` is provider-confirmed content for the mutually exclusive confirmed composition. When a target selects it dynamically, it replaces the request Form and composes `.password-reset__success.alert.alert--success` with Alert's polite announcement mapping. If removing the focused submitter would strand focus, the target focuses the Alert root or heading. Composition selection remains target-owned and does not introduce a public success boolean or neutral transition machine.

## Usage Guidelines

<DoDont>
  <Do>Use one generic confirmation that applies whether or not the identifier belongs to an account.</Do>
  <Dont>Do not reveal account existence through message text, response timing, field treatment, or alternate destinations.</Dont>
</DoDont>

- Keep the request concise and ask only for the target identifier required to deliver recovery instructions.
- Use canonical Input with a visible label, `name`, native input type, `autocomplete`, and target-connected text errors.
- Let the target own submission, pending/disabled policy, errors, retry, uniform response timing, rate limiting, abuse defenses, delivery, reset tokens, routes, and analytics.
- Treat `recover password` and `set a new password from a valid token` as separate flows. U2 covers only the first.
- Keep the request Form available for initial submission and truthful error correction or retry. Replace it with Alert only after provider confirmation; never render both compositions together.
- Omit the complete renderer when required title/guidance or both mutually exclusive content choices are absent.

## Accessibility

- Label the native section with its visible title through `aria-labelledby`.
- Associate the email Input with a visible label and preserve `type="email"`, `name="email"`, `autocomplete="email"`, `required`, native validation, keyboard submission, and reset.
- Connect target validation errors to the field in text; do not rely on color or an icon alone.
- Use canonical Alert with `role="status"` and `aria-live="polite"` only when confirmed feedback is dynamically inserted. Move focus only when replacement removes the focused control and would otherwise strand it.
- Keep the optional illustration `aria-hidden="true"`.
- Allow long localized or unbroken copy to wrap in narrow and zoomed layouts.

## Target Notes

- Neutral Web maps to a labelled section with canonical Form, Input, Button, and optional Alert, with zero U2 runtime.
- Shopify v1 current customer accounts use passwordless authentication, so U2 is intentionally omitted. Classic accounts can map the request step to Liquid `recover_customer_password`; `reset_customer_password` is the distinct token-backed new-password step in a separately versioned compatibility adapter.
- React, Angular, Hydrogen, SwiftUI, and Compose should keep request state external and preserve native target field, announcement, and security conventions.
- The registered Figma nodes resolve to generic Button documentation, not U2 artwork or visual approval.
