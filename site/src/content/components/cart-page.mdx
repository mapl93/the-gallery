## Overview

Cart Page is the named populated-cart composition. It combines one ordered
canonical Cart Line Item collection and one canonical Cart Summary from the
same target-confirmed cart snapshot, plus a required visible title, optional
target-formatted count, and optional complete continue-shopping link.

## Presentation

The root is a native `section` named by its visible title. Its `header` owns
only Cart Page context. A private neutral layout wrapper keeps the native line
list before the named summary in source order; neither wrapper adds a second
section or complementary landmark.

The layout responds to the Cart Page container, not the page viewport. Narrow
containers preserve one flow; a private wide threshold introduces a flexible
line-item track and a bounded summary track. `summaryPlacement` requests either
the default `sticky` presentation or explicit `flow` while preserving the same
source order and canonical Cart Summary. Sticky automatically degrades to flow
in narrow or short contexts. Page gutters and maximum width remain target-shell
decisions.

Cart Page represents a populated cart only. Cart Empty remains a separate
canonical component; the target atomically branches between them.

## Usage Guidelines

<DoDont>
  <Do>Replace the count, canonical line collection, and canonical summary together from one target-confirmed cart state.</Do>
  <Dont>Do not let Cart Page calculate prices, invent destinations, reimplement dependencies, or coordinate mutations independently.</Dont>
</DoDont>

- Supply a non-empty title, at least one canonical Cart Line Item, and one
  complete canonical Cart Summary. An invalid required composition omits the
  complete renderer.
- Include continue shopping only when both a descriptive label and real
  target-owned destination exist. There is no fallback URL.
- Treat `count` as localized snapshot text. Do not parse it as commerce data or
  make it a live region by default.
- Let one target coordinator own cart identity, persistence, inventory,
  pricing, quantity/removal transport, pending/error/rollback/retry, empty
  transition, checkout, focus, analytics, and cross-surface synchronization.
- Use `sticky` only in a target that owns the real header/safe-area offset,
  available height, collision boundary, zoom behavior and focused-control
  visibility. Degrade to `flow` whenever those guarantees cannot be met.

## Accessibility

- Name the native section from the required visible heading through a
  target-unique id. The target chooses the heading rank from the surrounding
  document outline; the docs renderer uses `h2`.
- Preserve Cart Line Item's native list, product identity, contextual controls
  and focus behavior, and Cart Summary's named native description list and
  canonical checkout Button.
- Keep the logical order title, optional context, lines, then summary even when
  the visual layout has two tracks.
- Keep continue shopping as a native link with ordinary Tab, Enter, modified
  activation, history, and context-menu behavior.
- After a confirmed mutation that changes content without navigation or focus
  context, announce one complete target-owned result such as “Quantity updated.
  Cart now has 2 items. Estimated total $240.” Do not make count, every line,
  and every total competing live regions.
- Preserve usability with keyboard-only operation, narrow containers, 200%
  zoom, user text spacing, long/localized content, RTL, dark mode, forced
  colors, and reduced motion.

## Target Translation

- **Web:** map `summaryPlacement` to the default sticky presentation or the
  `.cart-page--summary-flow` modifier. Canonical CSS handles width/height
  fallback and bounded overflow; a host with sticky chrome owns its real safe
  offset. No neutral JavaScript is required.
- **Shopify:** map `cart.items`, localized `cart.item_count`, the canonical
  Liquid line/summary snippets, the editor placement setting, native cart
  update form, checkout and a real collection route. Shopify remains
  responsible for its Header offset, server-authoritative refresh, errors,
  empty branching, editor behavior, accelerated checkout and live-store proof.
- **React and Angular:** expose a controlled composition over canonical
  dependencies. Framework state is a target concern, not a second Cart Page
  store.
- **Figma:** compose approved Cart Line Item and Cart Summary instances for the
  populated state after visual review. Registered generic nodes are
  traceability metadata, not final Cart Page artwork.
- **SwiftUI and Compose:** use target-native list, summary and navigation
  semantics while preserving the same data/lifecycle boundary.
