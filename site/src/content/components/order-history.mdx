## Overview

Order History is a passive, optionally named container for one required native list of target-owned order summaries. Each summary composes canonical Link and Badge with a semantic date and an already-formatted total.

## Presentation

`orders` is one required non-empty composition slot. Every native list item contains a descriptive Link, one `time[datetime]`, one readable Badge, and one formatted total. Identifier, destination, date, status, Badge variant, total, row count, ordering, pagination, and target lifecycle remain fixture or target data; they are not independent Order History properties.

The root is a named `section` only when `label` is non-empty. With no label, use an ordinary `div.order-list`; do not create an unnamed section. The row moves through private stacked, two-track, and four-area layouts according to its container width while DOM order stays number, date, status, total.

The shown status labels and Badge variants are target projections, not a canonical commerce taxonomy. Financial and fulfillment facts remain distinct in the target. U4 accepts one truthful localized Badge summary per row; when that cannot preserve the distinctions users need, use a richer target status composition outside U4 instead of inventing hidden U4 states.

## Usage Guidelines

<DoDont>
  <Do>Format dates, statuses, destinations, and totals from the same authoritative order record, then provide complete semantic values to the composition.</Do>
  <Dont>Do not infer order state from Badge color, create U4-specific status modifiers, or duplicate canonical Link and Badge behavior.</Dont>
</DoDont>

- Keep a real order-detail URL and descriptive visible Link text for each row.
- Use conforming machine-readable `datetime` values independently of localized visible date copy.
- Map target truth to canonical Badge variants only after choosing a readable status label.
- Compose loading, error, expired-session, empty, filtering, and pagination UI outside passive U4.
- Omit U4 when no complete order collection exists; do not render an empty list as if data loaded successfully.

## Accessibility

- Protect order history and destinations through the target authentication and authorization system.
- Use `label` only when U4 needs its own accessible section name; otherwise preserve ordinary grouped flow content.
- Keep native `ul/li`, Link, and `time` semantics. Visual grid areas do not create a grid widget or table.
- Preserve normal Tab, Enter, and modified native Link activation; do not make the complete row a second interactive surface.
- Expose every status as readable text and never through color alone. Static Badges are not live regions.
- Keep DOM/reading order stable at narrow widths and isolate already-formatted totals bidirectionally.

## Target Notes

- Target-controlled account views project protected authoritative order records through canonical U4. Platform-owned non-replaceable screens use a documented native handoff without claiming U4 visual or functional parity.
- Shopify v1 themes use the hosted current-account Order index rather than cloning it in Liquid. Full-page extensions and headless Customer Account API views are distinct target-controlled profiles; classic Liquid remains separately versioned compatibility.
- Pagination, loading, empty/error/expired state, authorization, status wording, dates, totals, navigation, announcements and focus recovery remain with the owning target surface.
