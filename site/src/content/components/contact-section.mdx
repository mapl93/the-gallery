## Overview

Contact Form arranges optional contact information beside one required named native form composed from Input, Textarea, and Button. It does not duplicate field values, validation, or submission behavior.

The parent owns only conditional section semantics, layout, introductory copy, details, a required form label, and the form slot. Input and Textarea retain their labels, names, values, constraints, messages, validation families, disabled/read-only state, focus, hover, and controlled/uncontrolled strategy; Button retains action state. The target owns the endpoint and complete response lifecycle.

## Usage Guidelines

<DoDont>
  <Do>Compose complete named field anatomy, keep the form short, and report only confirmed submission outcomes.</Do>
  <Dont>Do not recreate field variants, aggregate values, provider policy, or submit state as Contact Form properties.</Dont>
</DoDont>

Select is not a registered dependency of Contact Form. A target that supplies Select must preserve the Select contract rather than borrowing Input behavior.

Use `address` only for contact information relevant to the owning document or article. Keep unrelated hours, status, or promotional metadata in ordinary content. Actionable email and telephone values use native links.

## Accessibility

- Give the native form a non-empty localized accessible name. Associate every field with a visible label, give submitted controls stable names, and connect only field-specific supporting messages with `aria-describedby`.
- Use `aria-invalid="true"` only for Error fields; preserve equivalent Default, Success, and Warning anatomy.
- Keep native form submission and constraint validation. Communicate required fields visibly and announce only outcomes confirmed by the target service.
- Use native links for actionable contact details and preserve visible focus on all controls.
- For multiple validation failures, targets should provide a concise linked error summary and preserve entered non-sensitive values.
