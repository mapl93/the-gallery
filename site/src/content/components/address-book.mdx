## Overview

Address Book is a passive native collection of target-owned saved-address records. It can identify one default address with a canonical Badge and include canonical record or add-address actions without owning authentication, routing, or mutations.

## Presentation

`addresses` is one required slot containing a non-empty complete native list of saved-address records. Record identifiers must be unique, every record needs a recipient and at least one formatted postal line, and no more than one record may carry target-authoritative default truth. Recipient names, lines, ordering, and action availability are fixture or target data rather than Address Book properties. Missing, empty, duplicate, or incomplete required content omits the complete renderer.

`newAddressLabel` controls the non-empty visible text inside the optional `.address-card__new-action`. Blank content omits the final list item. The target owns navigation or disclosure into Address Form and all create, edit, delete, and default-address mutations. Delete requires confirmation or guaranteed undo; Set Default appears only when supported, and records/default truth remain unchanged until authoritative success.

## Usage Guidelines

<DoDont>
  <Do>Identify the default address with visible canonical Badge text.</Do>
  <Dont>Do not expose address data before the target authenticates and authorizes the customer.</Dont>
</DoDont>

- Format address lines according to their locale and target data model.
- Keep card actions concise and specific to the address they affect.
- Keep each saved-address record passive; do not imply whole-card activation around nested controls.
- Require explicit confirmation or an equivalent guaranteed undo path before destructive deletion, and keep the record present until authoritative success.
- Render Set Default only when the target supports it; preserve the current default marker until authoritative success.
- Restore focus deliberately after mutation success, cancellation, undo, or failure.

## Accessibility

- Protect address data behind the target authentication system.
- Preserve native `ul`/`li` semantics and use paragraphs, not the HTML `address` element, for arbitrary postal data.
- Expose the default state as readable canonical Badge text, not color alone.
- Give repeated actions names that include their visible label and identify the affected address.
- Implement record and add actions as canonical native Buttons or Links with visible focus.
- Announce the result of address mutations through target-owned feedback.

## Target Notes

- Target-controlled account views may project protected authoritative records through canonical U6. Platform-owned non-replaceable screens use documented native handoff without claiming U6 visual or functional parity.
- Shopify v1 uses hosted Profile/Addresses rather than a theme-owned clone. Supplementary extensions and headless Customer Account API views are distinct target-controlled profiles and must define B2B availability; classic Liquid remains separately versioned compatibility.
- The target owns permissions, confirmation/undo, pending/errors, concurrency, authoritative reconciliation, announcements, focus restoration, redaction and routing.
